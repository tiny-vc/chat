# 远端音轨与设备能力验收（2026-09-03）

## 验证方法

在原双端通话测试上同时开启 `TEST_CONNECTED_CALLS=true` 与 `TEST_REMOTE_AUDIO=true`，使用新的相同 TEST_RUN_ID。

CallPageState 增加仅供测试的只读远端音频统计接口，按对方用户 identity 查找实际接收音轨，返回订阅、静音状态及 WebRTC 接收包数/字节数；不读取音频内容、令牌或设备标签，不改变媒体传输行为。

每轮双方完成 LiveKit 连接后：

1. 确认订阅对方音轨且未静音，连续读取原生接收统计，要求包数和字节数相对首次有效读数均增长。从 audio-track-04 起同时检查本地发送计数增长，用于区分发送与接收侧的问题。
2. 双方通过真实按钮静音，握手后确认各自看到的远端 publication.muted 为 true；双方确认后才恢复麦克风，避免跨端时序掩盖断言。
3. 确认对方取消静音，再次验证接收统计增长。
4. 保留两轮通话、双方分别挂断、返回聊天页和 ENDED 历史断言。

进入测试前还通过实际 WebRTC 设备枚举读取摄像头输入数量，仅输出数量。无摄像头时不能把模拟器连接当作视频画面验收；本音频测试不伪造摄像头或视频帧。

## 边界

包数/字节增长证明客户端收到远端 RTP 音频数据，不证明人声可辨、无回声、扬声器实际出声或音量合适。静音断言是远端轨道元数据，不根据“零数据包”推断静音（协议仍可能发送保活/静音数据）。真机双向听感、输出路由、视频首帧和镜头切换需要另外验证。

## 当前结论与下一步

音频发布/订阅和通话 UI 不能替代实际 RTP 收发检查。跨轮两台模拟器都曾收到数据，但尚未在同一轮确认双向收发；静音同步和恢复收发断言也尚未到达，不能标记通过。

最新证据将当轮问题缩小到 A 本地发送计数为 0，而不是只在接收端丢失统计。双模拟器共享宿主音频设备、原生采集/音频会话及 SDK 行为都需要进一步区分；本轮未修改媒体连接逻辑、系统音频设备或 macOS 权限，也没有证据认定服务器故障。

下一步优先在两个独立音频设备上运行同一收发诊断（至少一端真机作对照），再验证远端静音、恢复发送、双向听感及输出路由。视频需有实际摄像头的设备；当前两台模拟器均枚举为 0。
